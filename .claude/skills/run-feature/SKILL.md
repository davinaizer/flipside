---
name: run-feature
description: Build the next unfinished feature from docs/features.json end to end (tasks, review, PR). Argument: a feature id such as F3, or "all". Default is the next feature only.
disable-model-invocation: true
---
You are the orchestrator. Argument: $ARGUMENTS (empty means the next feature only). Follow docs/WORKFLOW.md and the stop rules in CLAUDE.md. Do the implementation through the `implementer` subagent, not yourself.

1. Check `git status`. If the tree is dirty, a previous run was probably cancelled mid-task: show the changed files and ask whether to keep them for the task in progress or discard them. Discard only on the user's answer.
2. Look for a local `feat/<id>-*` branch whose PR is not merged (`gh pr list --head <branch> --state merged`). If one exists and it matches the argument, or there is no id argument, resume that feature and read the ledger from that branch: it stays in progress whatever its ledger says. Otherwise pick from the `develop` ledger: the given id, else the first with status not `done` whose `depends_on` are all `done`. None left: say the build is complete and list the manual checks still open.
3. If the feature has no tasks, stop and tell the user to run `/plan-backlog`. Do not plan inline.
4. Confirm before starting. Show a short summary: the feature and its dependencies, its requirements and ACs, the number of tasks and the first task (id, title, `done_when`), tasks marked `model: opus`, and the `manual_acs` you will leave for the user. When resuming, the count and the first task are those still `todo`. For `all`, list the features that will run. Then ask with AskUserQuestion: start, or stop. Do not create a branch or start any worker until the user confirms. Ask once per run, not per task.
5. Resuming: check out the existing branch. Otherwise `git checkout develop && git pull`, branch `feat/<id>-<slug>` from `develop`, set `branch` and status `in_progress` in the ledger, and commit that.
6. For each task with status `todo`, in order: start an `implementer` with the task id only (add the `model` override when the task has `model`). Wait for its report.
   - DONE: confirm the commit exists and the tree is clean.
   - BLOCKED: ask the user with AskUserQuestion using the worker's options, recommended first. Record the answer in `docs/decisions.md`, then re-dispatch the task with the answer in the brief.
7. Feature gate: run `bash scripts/verify.sh`, the e2e and axe checks for this feature's screens (if they exist), then start a fresh `reviewer` with the feature id and `git merge-base` range. After each review, append `REVIEW <id> round <n>: PASS|GAPS at <sha>` to `docs/progress.md` and commit it. On a resume, count the rounds from that log and skip the review if the last one is PASS and only that log line has changed since. For GAPS, create fix tasks and run them through `implementer`. After two review rounds with gaps remaining, ask the user.
8. Push the branch. If `gh pr view` finds an open PR for it, reuse that; otherwise open one with `gh pr create --base develop`. Set `pr` in the ledger, commit and push. Body: requirements and ACs with the evidence, the feature's `manual_acs` as a checklist, the ASSUMED lines from this feature, and any unresolved risk where verification was incomplete.
9. Merge only if all of these hold: verify, e2e and axe are green; the reviewer returned PASS; every task is `done`; the PR base is `develop`. First, on the feature branch, set status `done`, append to `docs/progress.md` (including `MANUAL PENDING: <ids>` for the feature's `manual_acs`), commit and push: agents cannot push to `develop`, so the ledger must reach it through the merge. Then run `gh pr merge --merge --delete-branch` (a merge commit keeps the per-task commits). Never merge into any other branch. If the merge is refused (for example branch protection), stop and ask. Then `git checkout develop && git pull`.
10. If the argument was `all`, continue with the next feature without asking again. Otherwise, or when the build is complete, stop and print: PRs merged, the ASSUMED items to review, all `MANUAL PENDING` checks, and how to undo a feature (`git revert -m 1 <merge sha>`). Remind the user to check `/usage`.

Keep your own context thin: read only worker reports, the ledger and the progress log, never the diffs the reviewer covers.
